1 Project Abstract

Memorize this! — This project presents an AI-Powered Smart Helmet that uses simulated IoT sensor data and a Random Forest Machine Learning classifier to predict rider safety conditions in real-time. The system monitors parameters like speed, vibration, alcohol level, drowsiness, acceleration, and gyroscope data. When a crash is predicted or rider impairment (alcohol/drowsiness) is detected, the system locks the vehicle ignition, triggers alarms, and broadcasts GPS coordinates via emergency SOS SMS to rescue services and family contacts — reducing the "Golden Hour" delay.

2 Problem Definition

ProblemExplanation
Intoxicated RidingAlcohol impairs reflexes and motor control, leading to accidents
Drowsiness / FatigueRider exhaustion causes micro-sleeps and swerving
Golden Hour DelayFatalities increase because emergency medical response is delayed — accidents happen without bystanders to report them

Key fact: Motorcycle riders represent a disproportionately high fraction of overall traffic fatalities globally.

What is the "Golden Hour"?

The Golden Hour refers to the first 60 minutes after a traumatic accident. Medical research shows that receiving treatment within this period significantly increases survival rates. Our project addresses this by automatically detecting crashes and instantly sending GPS-tagged SOS alerts — removing the dependency on bystanders.

5 Machine Learning Model — Deep Explanation

Algorithm: Random Forest Classifier

What is Random Forest? It is an ensemble learning method that builds multiple decision trees during training. Each tree is trained on a random subset of data (called bagging). The final prediction is decided by majority voting — whichever class gets the most votes wins. It prevents overfitting better than a single decision tree.

Classification Rules

🔴 DANGER conditions:

  • Vibration > 12.0 m/s² (crash impact)
  • Acceleration X or Y exceeds ±3.0G (violent collision)
  • Speed > 40 km/h AND vibration > 8.0 (high-speed crash)
  • Alcohol level ≥ 0.35 mg/L (heavily intoxicated)
  • Drowsy score ≥ 0.75 AND speed > 50 km/h (asleep while speeding)

⚠️ AT-RISK conditions:

  • Speed > 80 km/h (overspeeding)
  • Alcohol 0.15–0.35 (moderate alcohol)
  • Drowsy score 0.50–0.75 (moderate drowsiness)
  • Gyroscope X or Y > ±35°/s (unstable swerving)

✅ SAFE: All values within normal range

How Prediction Works at Runtime

# 1. Collect sensor readings into a feature array
features = [speed, vibration, alcohol_level, drowsy_score,
            accel_x, accel_y, accel_z, gyro_x, gyro_y, gyro_z]

# 2. Feed into the trained model
prediction = model.predict([features])          # Returns: 0, 1, or 2
probabilities = model.predict_proba([features]) # Returns: [0.92, 0.05, 0.03]

# 3. Map to human-readable status
status_map = {0: "Safe", 1: "At-Risk", 2: "Danger"}

Model Storage

The trained model is saved as helmet_model.joblib using the joblib library. On server startup, the model is loaded from disk (not retrained every time). If the file is missing, it auto-trains and saves a new one.

Background Simulation Thread

  • A daemon thread runs continuously in the background
  • Every 1 second, it generates new simulated sensor values based on the current demo mode
  • Passes values through the Random Forest model for prediction
  • Maintains a rolling history buffer of 20 readings for the charts

What is CORS?

CORS (Cross-Origin Resource Sharing) is a browser security feature. Since frontend runs on localhost:5173 and backend on localhost:8080, they are different "origins." Without CORS middleware, the browser would block API requests. We configure it in FastAPI to allow the frontend to communicate.

11 Anticipated Viva Questions & Answers

General Questions

Q1: What is the aim of your project?
To develop an AI-Powered Smart Helmet that uses Machine Learning to predict accidents, detect rider impairment (alcohol/drowsiness), and automatically send emergency SOS alerts with GPS location to reduce the Golden Hour delay.
Q2: What problem does this project solve?
It solves three problems: (1) detecting drunk riding and locking the ignition, (2) detecting drowsy riding and sounding alarms, and (3) detecting crashes and immediately sending SMS with GPS coordinates — eliminating dependency on bystanders.
Q3: Is this fully working hardware or software?
This is a 50% working software prototype. The complete software stack — ML model, API backend, real-time dashboard — is fully functional. The hardware integration with actual sensors is planned for the next phase.
Q4: Why did you choose this project?
Motorcycle accidents are a leading cause of road fatalities. Many deaths happen not because of the accident itself, but because emergency help arrives too late. Our project automates crash detection and emergency alerts to save lives during the Golden Hour.

Machine Learning Questions

Q5: What ML algorithm did you use and why?
We used Random Forest Classifier because: (1) it handles multi-class classification well, (2) it's robust against overfitting due to ensemble averaging, (3) it works well with tabular sensor data, and (4) it provides probability scores for confidence bars.
Q6: How many features does your model use?
10 features: speed, vibration, alcohol_level, drowsy_score, accel_x, accel_y, accel_z, gyro_x, gyro_y, gyro_z.
Q7: What are the output classes?
Three classes: Safe (label 0), At-Risk (label 1), and Danger (label 2).
Q8: How did you get the training data?
We generated 1500 synthetic training samples using numpy random functions with realistic sensor value ranges. Labels were assigned based on expert-defined rules — for example, vibration > 12.0 = Danger, speed > 80 = At-Risk.
Q9: What is the accuracy of your model?
The model achieves high accuracy (typically >95%) on the synthetic test set. In real-world deployment, accuracy would depend on actual sensor data calibration.
Q10: How many decision trees are in your forest?
80 decision trees (n_estimators=80), each with a maximum depth of 8 (max_depth=8).
Q11: What is overfitting? How does Random Forest prevent it?
Overfitting is when a model memorizes training data instead of learning general patterns. Random Forest prevents this by training multiple trees on random subsets of data (bagging) and averaging their predictions.
Q12: What is predict_proba?
It returns the probability distribution across all classes. For example, [0.92, 0.05, 0.03] means 92% Safe, 5% At-Risk, 3% Danger. We display these as confidence bars in the dashboard.

Backend Questions

Q13: Why FastAPI instead of Flask?
FastAPI is faster, supports async/await natively, auto-generates Swagger docs at /docs, has built-in data validation using Pydantic, and is the modern standard for Python APIs.
Q14: What is CORS and why do you need it?
CORS (Cross-Origin Resource Sharing) is a browser security feature. Since frontend runs on localhost:5173 and backend on localhost:8080, they are different origins. Without CORS middleware, the browser would block API requests.
Q15: How does real-time data work?
A background daemon thread generates new sensor values every 1 second. The frontend polls the /api/live-data endpoint every 1 second using setInterval to fetch the latest values and re-render the UI.
Q16: What happens when a crash is detected?
The system: (1) detects high vibration (18.7 m/s²) and G-force (5.2G), (2) drops speed to 0, (3) activates emergency alert with GPS coordinates, (4) simulates SOS SMS via GSM, and (5) generates a Google Maps link to the crash site.

Frontend Questions

Q17: Why React?
React is component-based, making it easy to build reusable UI elements. It efficiently updates only changed parts of the DOM using its virtual DOM — perfect for our dashboard that updates every second.
Q18: What is Vite?
Vite is a modern build tool significantly faster than Webpack. It uses native ES modules and Hot Module Replacement (HMR) for instant updates during development.
Q19: How do the charts work?
We use the Recharts library to render AreaCharts. The chart displays the last 20 historical data points (rolling buffer on the backend) for speed and vibration trends.

Hardware & Sensor Questions

Q20: What is the MPU6050?
It's a 6-axis sensor module with a 3-axis accelerometer (measures G-force) and a 3-axis gyroscope (measures angular velocity in °/s). Used to detect crashes, falls, and unstable riding.
Q21: How does the MQ-3 alcohol sensor work?
The MQ-3 has a tin-dioxide (SnO₂) sensitive layer. When ethanol vapor contacts this layer, its electrical resistance decreases proportionally to alcohol concentration. The analog output is read by the microcontroller.
Q22: What is the SW-420 vibration sensor?
It's a high-sensitivity vibration sensor using a spring-based comparator circuit. When mechanical vibrations exceed a threshold, it outputs a digital HIGH signal — used to detect collisions.
Q23: How does GPS tracking work?
The NEO-6M GPS module receives satellite signals and outputs NMEA formatted strings with latitude and longitude. These coordinates are parsed and included in the SOS SMS.
Q24: What is the SIM800L?
It's a GSM module that sends/receives SMS using a SIM card. We use AT commands to compose and send emergency SMS containing crash location and Google Maps links.

Architecture Questions

Q25: How does the frontend communicate with the backend?
Using JavaScript fetch() API to make HTTP requests. GET requests retrieve sensor data, POST requests change modes. Communication uses REST API with JSON format.
Q26: What is the complete data flow?
Sensor → ESP32 reads values → Sends to FastAPI via WiFi → Backend feeds into Random Forest → Predicts Safe/At-Risk/Danger → If crash detected → Activate alert → Send SMS via SIM800L with GPS → Dashboard shows SOS card.
Q27: Can this work with real hardware?
Yes! The software architecture is designed to accept real sensor data. Only the simulation code needs to be replaced with actual ESP32 hardware I/O — the API, ML model, and dashboard work unchanged.

12 Advantages & Disadvantages

Advantages

  1. Real-time accident prediction using ML reduces emergency response time
  2. Automated SOS eliminates dependency on bystanders
  3. Alcohol detection prevents drunk riding via ignition lockout
  4. Drowsiness alerts prevent fatigue-related accidents
  5. GPS-tagged alerts enable precise location for ambulances
  6. Modular architecture — easy to integrate real hardware later

Limitations

  1. Currently uses simulated sensor data, not real hardware
  2. ML model trained on synthetic data — real accuracy may vary
  3. Requires internet/cellular connectivity for SMS alerts
  4. GPS accuracy depends on satellite visibility
  5. Battery power management needs engineering for continuous operation
